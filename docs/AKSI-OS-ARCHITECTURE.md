# AKSI MATRIX — открытая архитектура системы

**Версия документа:** 0.1.0  
**Дата фиксации:** 2026-11-16  
**Статус:** проект архитектуры и карта фактической реализации, не заявление о готовой ОС.

## 1. Что строим

AKSI MATRIX развивается как browser-first интеллектуальная операционная среда: пользовательский интерфейс, диспетчер запросов, ограниченные вычислительные подсистемы, память, поиск, доказательства, безопасность и диагностика должны иметь явные контракты и наблюдаемые состояния.

**Точная граница:** сегодня AKSI — веб-приложение с JavaScript/Python-модулями и экспериментальным языком AKSI Q. Это не самостоятельная загрузочная ОС, не ядро Linux/Windows-класса и не изолированная операционная система с собственным драйверным слоем. Браузер остаётся хост-средой и задаёт ограничения доступа к процессору, памяти, сети, файлам и устройствам.

## 2. Архитектурные слои

| Слой | Назначение | Текущее состояние |
|---|---|---|
| Presentation | Главный экран, чат, панели источников, диагностика | Реализован частично; отдельные маршруты и кнопки требуют браузерного E2E-аудита |
| System API | Стабильные интерфейсы для подсистем, единые ошибки и статусы | Не унифицирован полностью |
| Kernel / Orchestrator | Жизненный цикл, маршрутизация задач, отмена, лимиты, приоритеты | Есть несколько маршрутизаторов и orchestration-модулей; единого ядра пока нет |
| Process model | Изолированные задачи, тайм-ауты, отмена, очереди | Не реализована как единая модель процессов |
| Memory | Краткосрочный контекст, пользовательская память, индекс знаний, хранилище артефактов | Частично: IndexedDB/localStorage и отдельные подсистемы |
| Compute | Калькулятор, символические правила, геометрия, симуляторы | Набор ограниченных движков; не единый вычислительный планировщик |
| Knowledge & Evidence | Поиск, извлечение, источники, оценка оснований, отказ при нехватке данных | Частично; извлечение не равно проверке истинности |
| Security | Разрешения, изоляция, безопасный ввод, управление секретами, аудит | Есть отдельные модули; сквозная модель угроз и enforcement требуют проверки |
| Observability | Журнал событий, метрики, диагностика, версии, причины отказов | Частично; требуется единый публичный формат состояния |
| Language & Toolchain | AKSI Q: лексер, парсер, типы, модули, runtime, компилятор | Ранний прототип; не production-язык и не средство полной миграции сайта |

## 3. Обязательные системные контракты

Каждый модуль должен предоставлять:
- уникальное имя и версию;
- заявленные возможности и зависимости;
- init() с явным результатом и диагностикой;
- status() без скрытого сетевого запроса;
- health() для проверок готовности;
- единый формат ошибок: код, этап, сообщение, исправимое действие;
- лимиты времени, размера входа и памяти, если применимо;
- явное описание сетевых и файловых разрешений;
- тесты успешного, ошибочного и граничного пути.

Никакой модуль не должен объявляться доступным только потому, что его файл загрузился. Состояния должны различать available, degraded, unavailable, not_configured и not_tested.

## 4. Модель выполнения задач

Целевой жизненный цикл задачи:

1. Принять запрос и выдать идентификатор задачи.
2. Проверить формат, размер и разрешения.
3. Выбрать исполнителя по явной таблице возможностей.
4. Запустить исполнение с тайм-аутом и лимитами.
5. Собирать события, источники, версии и ошибки.
6. Поддерживать отмену и безопасное завершение.
7. Проверить результат подходящим валидатором.
8. Вернуть ответ вместе с происхождением, ограничениями и статусом проверки.

Пока этот жизненный цикл не реализован как единый kernel API. Существующая маршрутизация не должна называться полноценной системой процессов.

## 5. Память и данные

Типы памяти должны быть разделены:
- session: временный контекст текущего диалога;
- user: пользовательские записи с понятным согласием и удалением;
- knowledge: документы и утверждения, добавленные в базу;
- evidence: фрагменты источников с URL, временем получения и хешем;
- execution: события и результаты выполнения;
- artifacts: файлы, созданные пользователем или системой.

Для каждого типа нужны владелец, область хранения, срок жизни, экспорт, удаление и модель доступа. Локальное хранилище браузера не является резервной копией и может быть очищено браузером.

## 6. Безопасность и открытость

- Внешний текст, веб-страницы и документы считаются недоверенными данными, а не инструкциями для системы.
- Секреты не помещаются в публичный репозиторий, клиентский код или журналы.
- Опасные действия требуют явного разрешения и ограниченного набора возможностей.
- Логи не должны записывать пароли, токены и лишние персональные данные.
- Публичная диагностика показывает состояние и причины отказов, но не раскрывает секреты и приватные данные.
- Криптографическая подпись подтверждает целостность/авторство ключа в рамках модели доверия, а не истинность содержимого.

## 7. Доказательства и честность

Статусы supported, contradicted и mixed допустимы только для явно записанных оценок с точной цитатой и данными о проверке. Поисковая выдача и лексическое совпадение не повышают статус доказательства.

Текущий лексический фильтр — только предварительная сортировка кандидатов. Он не понимает отрицание, причинность, контекст, временные условия, синонимы и логическое следование. Его проценты — доля совпавших терминов, а не вероятность истинности.

## 8. Этапы превращения в OS-подобную среду

1. **Baseline и прозрачность:** карта модулей, единый публичный статус, диагностические причины, воспроизводимые тесты.
2. **Kernel API:** единый загрузчик модулей, capability registry, жизненный цикл и единый error model.
3. **Task runtime:** очередь задач, отмена, тайм-ауты, лимиты и журнал событий.
4. **Memory service:** единый интерфейс памяти, миграции, экспорт/удаление и проверка приватности.
5. **Security boundary:** модель угроз, permissions, защита от prompt/source injection, аудит зависимостей.
6. **Evidence runtime:** атомарные утверждения, оценка фрагментов, benchmark с человеческой разметкой.
7. **AKSI Q toolchain:** единая грамматика, type checker, module system, runtime conformance; только затем компилятор и self-hosting как отдельные исследовательские цели.
8. **Browser E2E и release gates:** реальные сценарии в браузере, accessibility, offline/network failure, rollback и публичный changelog.

## 9. Критерии готовности

Нельзя называть систему ОС-подобной по факту наличия папки kernel/ или множества модулей. Каждый слой должен пройти:
- контрактные unit-тесты;
- интеграционные тесты через публичный API;
- тесты отказа и восстановления;
- браузерные E2E-сценарии;
- проверку разрешений и приватности;
- документированную оценку производительности и лимитов.

## 10. Текущая честная оценка

- Browser-first application: **да**.
- Отдельные подсистемы памяти, вычислений, поиска и доказательств: **да, частично**.
- Единое ядро с системными API и lifecycle: **нет, в разработке**.
- Полноценная модель процессов и ресурсов: **нет**.
- Самостоятельная загрузочная операционная система: **нет**.
- AKSI Q как production general-purpose language: **нет, ранний прототип**.
- Автоматическая семантическая проверка истинности источников: **нет**.

Это документ открытых требований и ограничений. Статус меняется только после реализации и проверок, а не после переименования модулей.
