# AKSI: ревизия и план доведения до проверяемого продукта
Дата: 2026-10-13
Статус: план работ; это не утверждение, что перечисленные задачи уже выполнены.

## Цель
Довести один сквозной сценарий от пользовательского интерфейса до backend и проверяемого результата. Не добавлять новые крупные подсистемы, пока этот сценарий не проходит тесты.

## Подтверждённая отправная точка
- Главный репозиторий: `MILANA808/milana808.github.io`.
- Backend: `MILANA808/Milana-backend`.
- В главном репозитории обнаружены интерфейсы, математические/агентные модули и криптографические компоненты.
- В backend есть FastAPI, API-маршруты, модули ядра и тесты.
- Успешный CI проверяет только включённые в него задания и не доказывает работоспособность всех функций или production-среды.

## Приоритет P0 — безопасность
1. Провести инвентаризацию всех мест хранения, импорта, экспорта и использования закрытых ключей.
2. Не хранить экспортируемые закрытые ключи в `localStorage`. Проверить XSS-границы и пути доступа к ключам.
3. Проверить конфигурацию секретов в production, включая `AKSI_PRIVATE_KEY_B64`; не выводить секреты в логи и отчёты.
4. Не заявлять о постквантовой защите без стандартизованного алгоритма и проверки реализации. Экспериментальный hash commitment не является постквантовой криптографией.
5. Для исправлений добавить регрессионные тесты. Не менять ключи production автоматически без анализа последствий и плана ротации.

## Приоритет P1 — единый сквозной сценарий
Сценарий: пользователь вводит задачу → frontend вызывает документированный API → backend валидирует вход → выполняет детерминированный инструмент/вычисление → проверяет результат → возвращает структурированный ответ → интерфейс отображает ответ и статус проверки.

Критерии приёмки:
- успешный сценарий покрыт интеграционным тестом;
- проверены неверный ввод, тайм-аут, недоступный провайдер и ошибка инструмента;
- UI показывает честное состояние, а не маскирует сбои;
- результат содержит метод/версию, входные данные или их безопасный отпечаток, статус проверки и ограничения;
- повторный запуск на фиксированных входных данных воспроизводим там, где это математически ожидается.

## Приоритет P2 — качество и поддерживаемость
1. Составить реестр ключевых модулей: назначение, точка входа, зависимости, тесты, статус интеграции.
2. Выявить дублирующиеся маршруты, провайдеры, форматы доказательств и механизмы памяти.
3. Зафиксировать единый формат отчёта и единый API-контракт.
4. Установить обязательные CI-проверки: тесты, линтер/форматтер, проверка зависимостей и поиск секретов.
5. Не считать наличие файла, названия «learning/quantum/AGI» или успешной сборки доказательством работающей функции.

## Приоритет P3 — пилот и коммерческая проверка
После прохождения P0/P1 выбрать одну задачу для пилота (например, проверяемые математические вычисления или воспроизводимый исследовательский отчёт). Показать её потенциальным пользователям, собрать обратную связь и проверить готовность платить до расширения платформы.

## Реестр подтверждений
- Код/файлы и конфигурации следует проверять непосредственно в репозиториях.
- Статусы CI следует перепроверять по конкретному коммиту и run.
- Production-работоспособность подтверждается отдельными smoke/integration tests и наблюдаемостью; она не выводится только из CI.

## Definition of Done
- [ ] Есть один описанный пользовательский сценарий.
- [ ] Frontend и backend проходят интеграционный тест.
- [ ] Ошибки и деградация видны пользователю.
- [ ] Нет необоснованных заявлений о постквантовой защите.
- [ ] Ключи и секреты проходят проверку безопасности.
- [ ] CI зелёный на целевом коммите.
- [ ] Демонстрация проверена на развёрнутой среде.
- [ ] Получена обратная связь хотя бы от одного внешнего пользователя.

## Важное ограничение
Этот документ — план ревизии и критерии приёмки. Он сам по себе не исправляет код, не доказывает отсутствие уязвимостей и не подтверждает production-статус.
